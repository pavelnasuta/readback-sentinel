# Правила работы с AI QC

## Роль проекта

Это внутренний инструмент первичного контроля начитки. Он формирует **кандидаты на проверку**, а не окончательные вердикты о браке.

## Непереговорные правила

1. Не отправляй замечания диктору автоматически. DOCX, CSV и финальный PDF формируются только из подтверждённых куратором флагов.
2. Не коммить аудио, тексты книг, глоссарии заказчика, результаты распознавания или персональные данные. В Git попадают только схемы, маленькие синтетические фикстуры и обезличенные метрики.
3. Не меняй правила классификации без теста, измерения на eval-наборе и записи в release note.
4. Не понижай пороги ради красивой метрики. Главный риск системы — ложные замечания диктору.
5. Любое изменение алгоритма выполняй на отдельной ветке. Не коммить напрямую в `main`.
6. Перед merge выполни unit-тесты и оценочный прогон; приложи результат «до / после» к релиз-ноте.

## Как работать над задачей

1. Создай issue или зафиксируй цель в `docs/tuning/`.
2. Сформулируй одну проверяемую гипотезу.
3. Сначала добавь тест либо кейс в eval-набор, который демонстрирует проблему.
4. Убедись, что тест падает или baseline фиксирует ошибку.
5. Внеси минимальное изменение.
6. Запусти тесты и сравни метрики с baseline.
7. Обнови `CHANGELOG.md` и создай `docs/releases/vX.Y.Z.md` по шаблону.
8. Только после проверки создай commit.

## Политика версий

- `PATCH` — исправление без изменения набора проверок или выходного контракта.
- `MINOR` — новая категория, новое правило, изменённая классификация или формат артефакта.
- `MAJOR` — несовместимый формат данных либо пересмотр стандарта качества.

## Hermes и cron

Cron используется только для коротких задач: проверки состояния репозитория, запуска тестов, подготовки сводки и запроса разметки. Hermes cron имеет ограничение времени выполнения; он не должен напрямую обрабатывать длинные аудиофайлы. Длинная обработка должна идти отдельным worker-процессом/очередью.

## Definition of done

Изменение считается готовым, только если:

- все изменённые функции имеют тесты;
- регрессии на eval-наборе не появились;
- метрики «до / после» зафиксированы;
- есть понятное человеческое описание изменения;
- известен rollback: git tag предыдущей стабильной версии.
